RetinaCare — Entity Relationship Diagram
=========================================

Source of truth : source/database/model/*.model.ts
Database        : MongoDB (Mongoose). Every collection has _id (ObjectId), __v (bumped on every
                  repository update) and createdAt / updatedAt (timestamps: true).
Notation        : Mermaid erDiagram. Paste the block into https://mermaid.live or any Markdown
                  viewer that renders ```mermaid blocks to see it drawn.

Legend for keys : PK = primary key, FK = reference (ObjectId ref), UK = unique index.
Cardinality     : ||--|| one-to-one, ||--o{ one-to-many (zero or more), }o--o{ many-to-many.

Indexes and constraints (from the schemas)
------------------------------------------
users               email UK; googleId UK sparse; role; text index on (name, email)
patients            user UK; medicalRecordNumber UK
doctors             user UK; licenseNumber UK sparse; verificationStatus
doctor_patients     (doctor, patient) UK — a pair is linked at most once; doctor; patient
fundusImages        patient; (patient, createdAt desc)
analyses            doctor; patient; status; (patient, createdAt desc); (image, createdAt desc)
doctor_reviews      (analysis, doctor) UK — one review per doctor per analysis; analysis; patient
reports             doctor; patient; (patient, createdAt desc)
doctor_availability (doctor, startAt) UK — a doctor cannot publish two slots that start together
appointments        (doctor, scheduledAt); (patient, scheduledAt)
conversations       (doctor, patient) UK — exactly one chat per doctor–patient pair; participants
messages            conversation; (conversation, createdAt desc)
notifications       recipient; (recipient, read, createdAt desc)


Design notes
------------
1. Every "doctor" and "patient" FK points to USER, not to DOCTOR / PATIENT. The DOCTOR and PATIENT
   collections are 1:1 profile extensions keyed by `user`, so authentication, chat and
   notifications only ever deal with user ids.
2. Sensitive or internal fields are `select: false` (passwordHash, googleId, storageKey,
   gradCamKey). They are loaded only on purpose with a projection such as '+passwordHash'.
3. ANALYSIS embeds its `findings` and `history` arrays (no separate collections): they are always
   read together with the analysis and never queried on their own.
4. NOTIFICATION.resourceId is polymorphic: its target collection is implied by `type`
   (appointment -> APPOINTMENT, report -> REPORT, analysis -> ANALYSIS, message -> CONVERSATION).
5. DOCTOR_AVAILABILITY.appointment and APPOINTMENT.slot reference each other. Both are written in
   the same operation when a slot is booked, and both are cleared when it is cancelled.
