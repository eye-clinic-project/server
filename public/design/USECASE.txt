RetinaCare — Use Case Model
===========================

Notation : PlantUML use-case diagrams. Mermaid has no use-case diagram type, so these blocks use
           PlantUML. Paste a block into https://www.plantuml.com/plantuml or open it with the
           VS Code / JetBrains PlantUML plugin.
Related  : API.txt (endpoint IDs such as AUTH-01), ACTIVITY.txt (flows such as A1), CLASS.txt, ERD.txt
Status   : [IMPLEMENTED] = in the code today; [PLANNED] = designed from the database model.


1. Actors
---------

Guest        Anyone who is not signed in. Can register, sign in, recover a password and browse the
             public doctor directory.
User         Abstract actor: any signed-in, active account. Patient, Doctor and Admin all
             specialise it and inherit its use cases (profile, notifications, sign-out).
Patient      A person with diabetes being screened. Owns their medical record, fundus images,
             results and reports.
Doctor       An ophthalmologist or physician. After an admin approves the licence, the doctor
             follows assigned patients, runs AI screening, confirms results and writes reports.
Admin        Platform operator. Verifies doctors, manages accounts and assignments, and watches
             platform statistics.
AI Service   External secondary actor (AI_* env vars). Grades fundus images in two stages: DR yes/no,
             then severity 0–4 with a Grad-CAM heat map.
Mail Server  External secondary actor (SMTP through @nestjs/mail). Delivers OTP codes and
             notification emails.
Google       External secondary actor (Google Identity Services and JWKS). Issues and signs the ID
             tokens used for Google sign-in.
Scheduler    Time-based system actor. Triggers follow-up reminders, appointment reminders and
             delayed notification emails.

3. Use case specifications
--------------------------

Format: ID / name / status. Primary actor, secondary actors, preconditions, trigger, main success
scenario, alternative and exception flows, postconditions, business rules, related API and
activity.

---------------------------------------------------------------------------------------------------
UC-01  Register account                                                            [IMPLEMENTED]
---------------------------------------------------------------------------------------------------
Primary actor   : Guest
Secondary actor : Mail Server
Preconditions   : The email is not registered. The client is within the sign-up rate limit (3 per hour).
Trigger         : The guest submits the sign-up form.
Main scenario   :
  1. The guest enters name, email, password (8–72 characters), city, role (patient or doctor) and
     accepts the terms.
  2. The system validates the input and normalises the email (trimmed, lowercased).
  3. The system checks that no account uses the email.
  4. The system hashes the password and creates the user with provider = system, the chosen role
     and consentAcceptedAt.
  5. The system issues an email verification code (include: Send OTP email) in the background.
  6. The system returns the new account (without secrets) and tells the guest to check their inbox.
Alternatives    :
  1a. Role = doctor: clinicName, clinicAddress and licenseNumber are also required. [PLANNED] A
      Doctor profile is created with verificationStatus = pending, and the admins are notified
      (continues in UC-12 and UC-13).
  3a. The email exists: 409 "user exist before". The guest is told to sign in or recover the
      password.
  5a. The mail server fails: the account is still created and the failure is logged. The guest
      can request a new code with UC-02.
Exceptions      : invalid input → 400; rate limit → 429.
Postconditions  : An unverified account exists. A hashed code for it is cached for 10 minutes.
Business rules  : Admin accounts can't be self-registered. Unknown fields are rejected.
Related         : AUTH-01 · ACTIVITY A1

---------------------------------------------------------------------------------------------------
UC-02  Verify email                                                                [IMPLEMENTED]
---------------------------------------------------------------------------------------------------
Primary actor   : Guest
Secondary actor : Mail Server
Preconditions   : The account exists and is not verified.
Trigger         : The guest opens the email and types the 6-digit code.
Main scenario   :
  1. The guest enters the email and the code.
  2. The system hashes the code and compares it, in constant time, with the stored hash.
  3. The system deletes the code (it works only once) and sets emailVerifiedAt.
  4. The system answers 204, and the client sends the guest to sign in.
Alternatives    :
  1a. The code is lost or expired: the guest asks for a new one (AUTH-05). The system always
      answers 202, and sends a code only if the account exists and is still unverified. The new
      code replaces the old one.
  2a. Wrong or expired code: 400 "Invalid or expired verification code". The guest can retry
      within the rate limit (5 per minute, then blocked for 1 hour).
Postconditions  : emailVerifiedAt is set and the account can sign in.
Business rules  : Codes are 6 digits and valid for 10 minutes. Only their HMAC-SHA256 is stored,
                  in the cache under auth:otp:email-verification:<email>. Responses never reveal
                  whether an account exists.
Related         : AUTH-05, AUTH-06 · ACTIVITY A2, A3

---------------------------------------------------------------------------------------------------
UC-03  Sign in                                                                     [IMPLEMENTED]
---------------------------------------------------------------------------------------------------
Primary actor   : Guest (registered user)
Preconditions   : The account exists, the email is verified and the account is active.
Trigger         : The guest submits email and password.
Main scenario   :
  1. The guest enters email and password.
  2. The system loads the account with its hidden password hash.
  3. The system checks that the email is verified, then checks the password.
  4. The system issues an access token and a refresh token and returns them.
  5. The client stores the tokens and loads the profile (UC-07) to decide which screens to show
     for the user's role.
Alternatives    :
  3a. Email not verified: 409. The client offers to resend the code (UC-02).
  3b. Wrong password: 401 "Invalid email or password".
  2a. Unknown email: 404. (Known issue: this reveals whether an email is registered. Planned: a
      single 401 for every failure, checked after the password.)
  2b. [PLANNED] Account disabled by an admin: 403, no tokens issued.
Exceptions      : rate limit 5 per minute, then blocked for 5 hours → 429.
Postconditions  : A new session (refresh token) exists for the user.
Related         : AUTH-02 · ACTIVITY A4

---------------------------------------------------------------------------------------------------
UC-04  Sign in with Google                                                [IMPLEMENTED in service]
---------------------------------------------------------------------------------------------------
Primary actor   : Guest
Secondary actor : Google
Preconditions   : Google sign-in is configured (OAUTH_GOOGLE_CLIENT_ID). The guest has a Google
                  account with a verified email.
Trigger         : The guest presses "Continue with Google".
Main scenario   :
  1. The client gets an ID token from Google and sends it to the system.
  2. The system checks the token's signature (Google JWKS), issuer, audience and expiry, and that
     Google verified the email.
  3. The system finds the account already linked to this Google subject.
  4. The system issues tokens (method = google).
Alternatives    :
  3a. No linked account and no account with this email (extends UC-01): the system needs a city
      (400 if it is missing), creates a verified patient account with provider = google and the
      Google picture as avatar, then continues at step 4.
  3b. An account with this email exists and is verified: the system links the Google subject to
      it with an atomic update and continues at step 4.
  3c. The account with this email is unverified: 403. The user must verify the email first, so
      nobody can take over an unverified account.
  3d. The email is already linked to another Google account, or a parallel request linked it
      first: 409.
Exceptions      : invalid token → 401; Google keys unreachable or not configured → 503.
Postconditions  : The user is signed in and the Google identity is linked.
Note            : the controller route is an empty stub right now and must be wired back to
                  AuthenticationService.googleSignIn.
Related         : AUTH-09 · ACTIVITY A6

---------------------------------------------------------------------------------------------------
UC-05  Recover password                                                            [IMPLEMENTED]
---------------------------------------------------------------------------------------------------
Primary actor   : Guest
Secondary actor : Mail Server
Preconditions   : None. The use case starts the same way whether or not the account exists.
Trigger         : The guest clicks "Forgot password".
Main scenario   :
  1. The guest enters the email. The system answers 202 right away.
  2. If the account exists, the system emails a password-reset code (6 digits, 10 minutes).
  3. The guest enters the email, the code and a new password.
  4. The system checks and uses up the code, saves the new password hash, and marks the email
     verified if it wasn't already.
  5. The system revokes every session of the account and answers 204.
  6. The guest signs in with the new password (UC-03).
Alternatives    : 4a. Wrong or expired code → 400. The guest can request a new code (back to step 1).
Postconditions  : The password is changed and every device is signed out.
Business rules  : The response never reveals whether an account exists. Codes are stored hashed.
Related         : AUTH-07, AUTH-08 · ACTIVITY A5

---------------------------------------------------------------------------------------------------
UC-06  Keep session / sign out                                                     [IMPLEMENTED]
---------------------------------------------------------------------------------------------------
Primary actor   : User (Patient, Doctor, Admin)
Main scenario   :
  1. When the access token expires, the client sends the refresh token and receives a new pair
     (AUTH-03).
  2. The user signs out of this device: the system revokes that refresh token.
Alternatives    :
  2a. "Sign out everywhere": every refresh token of the user is revoked (type = all), for example
      after losing a phone.
  1a. The refresh token is revoked or expired: 401, and the client goes back to sign-in.
Postconditions  : The revoked sessions can no longer be refreshed.
Related         : AUTH-03, AUTH-04 · ACTIVITY A7

---------------------------------------------------------------------------------------------------
UC-07  Manage own profile                                                          [IMPLEMENTED]
---------------------------------------------------------------------------------------------------
Primary actor   : User
Preconditions   : Signed in, and the account is active (UserPolicy).
Main scenario   :
  1. The user opens "My profile". The system returns the profile without secrets, with
     emailVerified as a boolean.
  2. The user changes name and/or city and saves.
  3. The system updates only those fields and returns the updated profile.
Alternatives    : 2a. Any other field (email, role…) → 400. Those fields can't be edited here.
Exceptions      : not signed in → 401; disabled → 403; account deleted → 404.
Related         : USER-01, USER-02 · ACTIVITY A8

---------------------------------------------------------------------------------------------------
UC-08  Manage avatar                                                               [IMPLEMENTED]
---------------------------------------------------------------------------------------------------
Primary actor   : User (uploads, replaces or removes); Guest or anyone (views)
Main scenario   :
  1. The user picks a JPEG, PNG or WebP image of 5 MB or less.
  2. The system stores it under avatars/<userId>/<random>.<ext> on the photos disk, saves the key
     and the public URL, and deletes the previous file.
  3. Any client shows the avatar through its public URL. The image is served inline and can be
     cached for a year.
Alternatives    :
  1a. No file, wrong type or too large → 400 or 413.
  2a. The user removes the avatar: the key and URL are cleared and the file is deleted. If there
      is no avatar → 404.
  3a. Malformed URL → 400. Missing file or non-image file → 404. SVG is never served.
Related         : USER-03, USER-04, USER-05 · ACTIVITY A8

---------------------------------------------------------------------------------------------------
UC-09  Manage patient medical profile                                                  [PLANNED]
---------------------------------------------------------------------------------------------------
Primary actor   : Patient. Secondary: the assigned Doctor (clinical notes).
Main scenario   : 1. The patient views their medical record number and profile. 2. The patient
                  updates date of birth, gender, emergency contact and year of diabetes onset.
                  3. The system saves the changes.
Alternatives    : 2a. medicalNotes and medicalRecordNumber are read-only for the patient. Only an
                  assigned doctor can write medicalNotes (UC-17).
Business rules  : medicalRecordNumber is unique and uppercase, and is generated by the system.
Related         : PAT-01, PAT-02, PAT-04

---------------------------------------------------------------------------------------------------
UC-10  Manage doctor profile                                                           [PLANNED]
---------------------------------------------------------------------------------------------------
Primary actor   : Doctor
Main scenario   : 1. The doctor views their profile and verification status. 2. The doctor edits
                  clinic name and address, specialty, bio and years of experience. 3. The system
                  saves the changes.
Alternatives    : 2a. The licence number changes after approval: the status goes back to pending
                  and the admins are notified (UC-13). 2b. The licence is already in use → 409.
Related         : DOC-03, DOC-04

---------------------------------------------------------------------------------------------------
UC-11  Browse doctor directory                                                         [PLANNED]
---------------------------------------------------------------------------------------------------
Primary actor   : Guest or Patient
Main scenario   : 1. The actor filters doctors by city or specialty. 2. The system lists approved,
                  active doctors with their public details. 3. The actor opens a profile and can
                  request that doctor (UC-14, patients only).
Business rules  : Pending or rejected doctors, licence numbers and verification data are never
                  shown. Anonymous results are cached.
Related         : DOC-01, DOC-02

---------------------------------------------------------------------------------------------------
UC-12  Submit / resubmit doctor verification                                           [PLANNED]
---------------------------------------------------------------------------------------------------
Primary actor   : Doctor
Preconditions   : The doctor signed up with role doctor (UC-01, alternative 1a).
Main scenario   : 1. The verification is submitted with the licence details at sign-up (status
                  pending). 2. The doctor checks the status (DOC-03) and waits. 3. The admin
                  decides (UC-13).
Alternatives    : 3a. Rejected: the doctor reads rejectionReason, fixes the profile (UC-10) and
                  resubmits (DOC-05). The status goes back to pending and verificationSubmittedAt
                  is reset.
Postconditions  : The verification is in the admin queue.
Business rules  : Until the doctor is approved, every doctor-only use case (UC-15, UC-17 to UC-22,
                  UC-25) is refused with 403.
Related         : DOC-03, DOC-05 · ACTIVITY A9

---------------------------------------------------------------------------------------------------
UC-13  Verify doctor                                                                   [PLANNED]
---------------------------------------------------------------------------------------------------
Primary actor   : Admin. Secondary: Mail Server.
Main scenario   :
  1. The admin opens the queue of pending doctors (oldest first).
  2. The admin checks the licence number and clinic details outside the system.
  3. The admin approves. The system records verifiedAt and verifiedBy and notifies the doctor in
     the app and by email.
Alternatives    : 3a. The admin rejects with a reason. The doctor is notified with that reason
                  (back to UC-12).
Postconditions  : The doctor can use the doctor panel, or knows why not.
Related         : ADM-01, ADM-02, ADM-03 · ACTIVITY A9

---------------------------------------------------------------------------------------------------
UC-14  Request a doctor                                                                [PLANNED]
---------------------------------------------------------------------------------------------------
Primary actor   : Patient
Preconditions   : The doctor is approved. The pair has no pending or active link.
Main scenario   : 1. The patient picks a doctor in the directory and sends a request with an
                  optional note. 2. The system creates a pending assignment and notifies the
                  doctor.
Alternatives    : 1a. A link already exists → 409. 1b. A previously ended link is re-opened as
                  pending.
Related         : ASG-01 · ACTIVITY A10

---------------------------------------------------------------------------------------------------
UC-15  Accept / decline / end assignment                                               [PLANNED]
---------------------------------------------------------------------------------------------------
Primary actor   : Doctor (accept, decline or end); Patient (cancel or end)
Main scenario   : 1. The doctor reviews pending requests. 2. The doctor accepts. The system makes
                  the assignment active, creates the pair's conversation and notifies the patient.
Alternatives    : 2a. The doctor declines: the assignment becomes ended and the patient is
                  notified. 3a. Either side ends an active relationship: ended, endedAt is set,
                  the chat becomes read-only, and new uploads and bookings are blocked. The
                  medical history is kept.
Related         : ASG-02, ASG-03, ASG-04 · ACTIVITY A10

---------------------------------------------------------------------------------------------------
UC-16  Assign patient to doctor                                                        [PLANNED]
---------------------------------------------------------------------------------------------------
Primary actor   : Admin
Main scenario   : The admin selects a doctor and a patient. The system creates an active
                  assignment with assignedBy = the admin, and notifies both users.
Related         : ASG-05

---------------------------------------------------------------------------------------------------
UC-17  View patient chart                                                              [PLANNED]
---------------------------------------------------------------------------------------------------
Primary actor   : Doctor (approved, assigned). Admin can view all charts.
Main scenario   : 1. The doctor searches their patient list. 2. The doctor opens a chart: profile,
                  images, analyses, reviews, reports and appointments (includes UC-24). 3. The
                  doctor adds or edits clinical notes.
Exceptions      : patient not assigned → 403.
Related         : PAT-03, PAT-04

---------------------------------------------------------------------------------------------------
UC-18  Upload fundus image                                                             [PLANNED]
---------------------------------------------------------------------------------------------------
Primary actor   : Doctor (for an assigned patient) or Patient (for themself)
Preconditions   : An active assignment (for doctors). JPEG or PNG within MAX_IMAGE_SIZE_MB.
Main scenario   :
  1. The actor selects the image, the eye (left, right or unknown), the capture date and notes.
  2. The system computes the sha256 and checks for a duplicate.
  3. The system stores the file privately and records the image metadata and the uploader.
  4. The system starts an AI analysis (include: UC-19) and answers 202 with the analysis id.
Alternatives    : 2a. The same image was already uploaded for this patient: the existing record
                  is returned and no new analysis is started.
Exceptions      : wrong type or size → 400 or 413; not allowed → 403; rate limit 20 per minute.
Postconditions  : The image is in the patient's history and an analysis is pending.
Related         : IMG-01, IMG-02, IMG-03 · ACTIVITY A11

---------------------------------------------------------------------------------------------------
UC-19  Run AI analysis                                                                 [PLANNED]
---------------------------------------------------------------------------------------------------
Primary actor   : System (queue worker); started by UC-18 or by a doctor's re-run
Secondary actor : AI Service
Main scenario   :
  1. The worker marks the analysis processing and increments attempts.
  2. The AI service runs stage 1: DR or no DR, plus probabilities for the eight findings.
  3. If DR is present, the AI service runs stage 2: grade 0–4 with probabilities and a Grad-CAM
     heat map.
  4. The system stores the results, model version and processing time, and marks the analysis
     completed.
  5. The system notifies the patient and the assigned doctors (UC-29).
Alternatives    :
  2a. No DR: predictedLevel = 0 and stage 2 is skipped.
  2b. The AI call fails: it is retried until the maximum number of attempts. After that the
      status is failed, the error is recorded, and the users are notified.
  2c. AI_MODE=mock: the results are flagged isMock and shown as "demo — not a diagnosis".
Postconditions  : The analysis is completed or failed, and every status change is in history.
Related         : ANA-01, ANA-05 · ACTIVITY A11

---------------------------------------------------------------------------------------------------
UC-20  View analysis result                                                            [PLANNED]
---------------------------------------------------------------------------------------------------
Primary actor   : Patient (own results); Doctor (assigned patients)
Main scenario   : 1. The actor opens an analysis. 2. The system shows the status, DR yes/no, the
                  grade with its label and plain-language description (in the user's language),
                  the confidence, the class probabilities and the findings. 3. The doctor can
                  view the Grad-CAM heat map.
Alternatives    : 2a. Not reviewed yet: the patient sees "pending doctor review". 2b. Reviewed:
                  the doctor's confirmed grade is shown instead of the AI grade. 2c. Still
                  processing: the status is shown, and the client polls or waits for a
                  notification.
Related         : ANA-02, ANA-03, ANA-04

---------------------------------------------------------------------------------------------------
UC-21  Review AI result                                                                [PLANNED]
---------------------------------------------------------------------------------------------------
Primary actor   : Doctor (approved, assigned)
Preconditions   : The analysis is completed. This doctor hasn't reviewed it yet.
Main scenario   :
  1. The doctor examines the result (includes UC-20) and the image.
  2. The doctor confirms the AI grade, or overrides it with their own grade.
  3. The doctor adds notes, recommendations and an optional follow-up date.
  4. The system saves the review. The confirmed grade becomes the grade of record.
Alternatives    : 3a. A follow-up date is set: the Scheduler sends a follow_up reminder on that
                  date. 4a. Already reviewed → 409; the doctor edits the review instead (REV-02),
                  which is allowed until a sent report references it.
Postconditions  : The analysis is clinically signed off. Overrides are recorded for monitoring
                  the model.

UC-26  Book appointment                                                                [PLANNED]
---------------------------------------------------------------------------------------------------
Primary actor   : Patient (assigned to the doctor)
Main scenario   :
  1. The patient views the doctor's free slots in a date range.
  2. The patient picks a slot and gives a reason.
  3. The system claims the slot atomically, creates a pending appointment and notifies the doctor.
Alternatives    : 3a. Another patient booked the slot first → 409 "Slot already booked". The
                  patient picks another one.
Postconditions  : The slot is booked and linked to the appointment.
Related         : APT-01, AVL-02 · ACTIVITY A13

Alternatives    : 1a. Either side cancels with a reason: the slot is freed and the other side is
